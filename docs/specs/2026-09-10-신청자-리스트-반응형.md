# 신청자 리스트 — PC·모바일 반응형 개편

실서버에 배포된 이벤트 신청자 관리 화면(이벤트 페이지 › `신청자 보기` 모달)을 고친다.

- 프로토타입 · [applicant-list-0910](../../prototypes/applicant-list-0910/)
- 대상 화면 · `screens/event-applicants-check.html`

## 문제

**"목록"인데 실제로는 모든 신청자의 상세를 세로로 이어붙인 화면이다.**
한 명당 항목이 8~12개씩 전부 펼쳐져 있어 22명이면 화면 수십 개 분량이 된다.

여기서 세 가지가 파생된다.

**PC 폭을 못 쓴다.** 모달 폭이 1000px 정도로 고정인데, 폭이 넓어져도 한 명씩 세로로 쌓이는
구조라 여백만 늘어난다.

**모바일에서 내용이 안 보인다.** 고정 헤더가 7줄(제목 · 관리자/사용자 토글 · 받고 있는 정보
5줄 · 총원 · 탭 · 타임 칩 2줄)이라 스크롤 영역에 남는 자리가 거의 없다.

**긴 라벨이 세로로 접힌다.** 상세의 라벨 컬럼이 90px밖에 안 돼서
`(대표자) [필수항목] 개인정보 수집, 이용 제공에 동의하십니까?`가 5줄로 접히는데, 값은
`동의합니다.` 한 줄이다. 한 항목이 다섯 줄을 먹는다.

## 무엇을 위한 화면인가

주최측이 이 화면에서 하는 일은 두 가지다.

1. **승인·거절 처리** — 기본은 승인이고 이상한 건만 걸러낸다
2. **전체 훑어보기** — 누가 신청했는지, 타임별로 얼마나 찼는지

판단 기준은 **자리·인원 상황**과 **동의 여부**다. 장학금 사연 같은 긴 답변을 읽고 판단하지는
않는다. 그러므로 **상세는 필요할 때만 열면 된다.**

## 설계

### 1. 컨테이너

진입 경로(이벤트 페이지 › `신청자 보기`)는 그대로 두고 모달을 키운다.

| | 지금 | 바꾸면 |
|---|---|---|
| PC | 폭 약 1000px 고정 | 폭 최대 **1280px**, 높이 **90vh** |
| 모바일 | 위아래 여백을 남긴 모달 | **화면 전체**(100dvw × 100dvh) |

모바일에서 모달 위아래에 배경이 보이는 여백은 낭비다.

### 2. 목록 — 한 줄에 한 신청

```
PC
☐  대나무 밭 2명   재학생   2타임    승인 대기  [승인][거절]  09.09 21:52
☐  이희철         졸업생   미배정   승인 대기  [승인][거절]  09.10 04:13

모바일
☐  대나무 밭 2명                    승인 대기
   재학생 · 2타임 (19:00~19:50)
   [승인] [거절]        2026.09.09 21:52
```

같은 줄이 PC에서는 컬럼으로 늘어서고 모바일에서는 두 줄로 접힌다. **레이아웃을 두 벌 만들지
않는다.**

**컬럼은 일곱 개로 고정한다.** 시스템이 이벤트와 무관하게 늘 아는 값들이다.

| 컬럼 | 값 |
|---|---|
| 선택 | 체크박스 |
| 이름 | 개인은 이름, 팀은 팀명 + 인원 |
| 유형 | 참가 유형 이름 |
| 자리 | 배정된 타임 또는 `미배정` |
| 상태 | 아래 다섯 가지 |
| 액션 | 상태에 따라 `승인` `거절` 또는 `삭제` |
| 신청일 | 날짜 · 시각 |

**참가 유형마다 흐름이 다르다.** 이번 행사는 이렇게 나뉜다.

| | 자리 | 승인 | 상태 |
|---|---|---|---|
| **재학생 팀** | 타임 배정 | 팀원 동의 후 운영자 승인 | `승인 대기` → `승인` · `거절` · `신청 실패` |
| **졸업생** | 쓰지 않음 | 없음 — 신청과 동시에 완료 | `신청 완료` |

자리를 쓰지 않는 유형은 자리 칸을 `—`로 비운다. `미배정`은 자리를 기다린다는 뜻이라
자리 개념이 없는 유형에 쓰면 틀린 말이 된다.

**상태는 여섯 가지다.**

| 상태 | 뜻 | 버튼 |
|---|---|---|
| `승인 대기` | 아직 판단 전 (재학생 팀) | `승인` `거절` |
| `승인` | 자리 확정 · QR 발급 | `삭제` |
| `신청 완료` | 승인 없이 바로 확정 (졸업생) | `삭제` |
| `거절` | 운영자가 받지 않기로 함 | `삭제` |
| `신청 실패` | 팀원 미달 등으로 무효 | `삭제` |
| `신청 취소` | 신청자가 스스로 뺌 | `삭제` |

**판단은 승인 대기에서 한 번만 한다.** 승인이든 거절이든 알림이 이미 나간 뒤라 되돌리지 않는다.

**삭제는 승인 대기에서만 못 한다.** 아직 처리할 일이 남은 건을 지우면 신청자는 아무 소식도
못 받는다. 판단부터 하고 지운다. 되돌릴 수 없으므로 지우기 전에 한 번 묻는다.

**삭제는 지우기 전에 한 번 묻는다.** `건축 다섯 (5명) — 되돌릴 수 없어요.`처럼 무엇을 지우는지
확인시킨다. 팀이면 인원도 같이 보여준다.

그래서 한 줄에는 **승인·거절이 있거나 삭제가 있거나** 둘 중 하나만 나온다.
체크박스도 승인 대기에만 준다. 일괄 처리에서 아무 일도 일어나지 않을 건을 고르게 두면
"몇 건 승인"이라는 숫자가 거짓말이 된다.

**메타 컬럼은 폭을 고정한다.** 남는 폭은 이름만 먹는다. 액션 칸이 버튼 개수에 따라 늘었다
줄었다 하면 앞의 열까지 밀려서 줄마다 시작점이 어긋난다.

**자리 우선순위는 상세 맨 위에 둔다.** 대표자가 고른 순서(`1 2타임` `2 1타임`)가 어디에 넣을지
판단하는 근거이므로, 상세를 열자마자 보여야 한다. 자리를 쓰는 유형에만 있다.

**신청폼 항목은 줄에 넣지 않는다.** 이벤트마다 달라서 고정 컬럼이 될 수 없고, 목록에 보일
항목을 고르는 설정을 새로 만들지도 않는다. 전부 상세에서 본다.

**팀은 한 줄로 접는다.** 줄을 누르면 그 아래로 대표자 정보와 팀원 카드가 펼쳐진다.
지금처럼 항상 펼쳐져 있지 않다.

**펼친 줄의 아래 경계는 두껍게 둔다.** 줄 사이 구분선과 굵기가 같으면 상세가 어디서 끝나고
다음 신청이 어디서 시작하는지 안 보인다. 8px 회색 띠로 한 덩어리가 끝났음을 보여준다.

**펼친 줄은 상단에 붙는다.** 팀원 다섯 명을 훑다 보면 어느 신청을 보고 있었는지 놓친다.
붙어 있는 줄에 승인·거절 버튼도 함께 있어 스크롤 중에 그대로 처리할 수 있다.
모바일에서는 줄이 세 층이라 110px을 차지하지만, 어느 팀인지 모르는 채 읽는 것보다 낫다.

### 3. 상세 — 줄을 누르면 펼쳐진다

**라벨을 값 위로 올린다.**

```
지금                                바꾸면
(대표자) [필수      동의합니다.      (대표자) [필수항목] 개인정보 수집,
항목] 개인정보                       이용 제공에 동의하십니까?
수집, 이용 제                        동의합니다.
공에 동의하십
니까?
```

**한 열로 쌓는다.** 두 열로 놓으면 세로 길이는 줄지만 읽는 순서가 갈린다. 질문과 답을 위에서
아래로 한 방향으로 읽는 편이 낫다. 폭이 넓을 때 한 줄이 지나치게 길어지지 않도록 답변에
상한(88자)을 둔다.

**객관식 답은 알약 안에 넣는다.** 고른 보기와 직접 쓴 답을 눈으로 구분할 수 있어야 한다.
`동의합니다.` `예`처럼 짧은 답이 텍스트로만 있으면 주관식 답과 섞여 보인다.
알약은 주변 답변보다 한 단계 작고 굵기는 같다 — 고른 보기가 더 중요할 이유는 없다.

**파일 업로드 답은 다운로드 버튼으로 만든다.** 파일명은 읽는 값이 아니라 받아 가는 것이다.
이름이 길면 말줄임으로 자른다.

**항목 사이에 옅은 선을 둔다.** 질문과 답이 번갈아 쌓이기만 하면 어디까지가 한 항목인지
경계가 흐려진다.

**답은 예외 없이 질문 아래에 둔다.** 짧은 라벨만 옆에 두면 항목마다 모양이 달라져 오히려
읽기 어렵다. 팀원이 많을 때 오른쪽 열이 길어지는 것은 감수한다.

**팀이면 왼쪽은 신청 정보, 오른쪽은 사람으로 가른다.**

```
┌─ 신청 정보 ──────────────┬─ 팀원 2명 ──────────┐
│ [필수] 개인정보 수집…       │ 김형우      대표자    │
│   동의합니다.               │   전화번호 …         │
│ 장학금 사연                 │ ──────────────      │
│   취준생과 대학원준비생입니다.│ 김범룡              │
│ 학과   경제학부             │   전화번호 …         │
└──────────────────────────┴────────────────────┘
```

**팀원은 세로로 쌓는다.** 좌우로 두 장씩 놓으면 인원이 홀수일 때 한 칸이 비고, 항목 수가 다르면
짧은 쪽 카드 아래가 텅 빈다.

개인 신청은 팀원이 없으므로 한 열만 쓴다. 모바일은 위아래로 쌓는다.

### 4. 헤더 — 7줄에서 2줄로

| 지금 고정 영역에 있는 것 | 어디로 |
|---|---|
| 받고 있는 정보 5줄 | `ⓘ` 버튼 안으로. 한 번 확인하는 정보다 |
| 관리자 보기 / 사용자 보기 | 제목 옆 **스위치 탭**으로. 화면 전체의 의미가 바뀌는 전환이라 보여야 한다 |
| 총 N명 신청 | 탭 줄 오른쪽 끝으로. 건수가 아니라 **사람 수**를 센다 |
| 엑셀 다운로드 | `⋯` 메뉴 안으로. 하루 한 번 쓰는 동작이다 |
| 유형 탭 | 그대로. 옆에 `승인 대기 N` 토글이 붙는다 |
| 타임 칩 | 그대로 — 자리를 보고 판단하므로 |

```
PC ─ 두 줄이 모두 고정
┌──────────────────────────────────────────────────────────────┐
│ 신청자 리스트          [관리자 보기|사용자 보기]     ⓘ   ⋯   ✕ │
│ 전체  재학생  졸업생   1타임 21/80  2타임 10/80  3타임 7/80  22명│
├──────────────────────────────────────────────────────────────┤
│ ☐ 대나무 밭 2명   재학생  2타임 (19:00~19:50)  승인 대기  …    │

모바일 ─ 위 두 줄만 고정, 타임 칩은 스크롤과 함께 올라간다
┌──────────────────────┐
│ [관리자|사용자]  ⓘ ⋯ ✕│  고정 · 제목은 자리가 없어 뺀다
│ 전체 재학생 졸업생  22명│  고정
├──────────────────────┤
│ 1타임 21/80  2타임 → │  가로 스크롤
│ ☐ 대나무 밭 2명 승인대기│
```

**승인 대기만 보는 토글을 둔다.** 유형 탭 옆에 `승인 대기 2`. 켜면 대기 건만 남고 라벨이
`전체 보기`로 바뀐다.

승인이 이 화면의 주 용도이므로, 매일 여는 경로가 **재학생 탭 → 승인 대기 → 전체 선택 → 승인**
한 줄이 되게 한다.

**승인을 쓰는 유형에서만 나온다.** 졸업생은 신청과 동시에 완료되어 승인 대기라는 상태가 없다.
전체 탭에서도 감춘다 — 승인은 재학생 팀의 개념이므로 그 탭에서 하는 것이 맞다.
대기 건이 0이면 토글도 사라진다. 탭을 옮기면 토글이 풀린다.

**받고 있는 정보(`ⓘ`)는 폼 구조를 그대로 보여준다.**

```
재학생 팀  7개
  · 팀 이름
  · 자리 우선순위
  · (대표자) …
  ┌ 팀원 정보  7개      ← 들여쓰기 + 세로선으로 하위임을 표시
  │ · 이름
  │ · 전화번호
졸업생  10개
  · 이름
```

`팀원 정보`는 재학생 팀의 **하위**다. 나란히 놓으면 팀 폼과 팀원 폼이 별개로 읽힌다.
항목은 한 줄에 하나씩 — 스물세 개를 점으로 이어 붙이면 어디서 끊기는지 안 보인다.
묶음마다 개수를 붙여, 팀 신청 한 건이 실제로는 7 + (7 × 인원)개를 받는다는 것이 드러나게 한다.

**모바일에서는 제목을 뺀다.** 390px에서 제목·스위치 탭·아이콘 셋이 한 줄에 안 들어간다.
모달이 화면 전체를 덮고 스위치 탭에 `관리자 보기`가 있어 어떤 화면인지는 알 수 있다.

PC에서 탭과 타임 칩이 2줄로 접히는 것은 모달이 좁아서다. 1280px에서는 한 줄에 들어간다.

**모바일에서 고정은 두 줄까지만.** 타임 칩까지 고정하면 목록이 처음부터 안 보인다. 자리를
확인하고 싶으면 위로 조금 올리면 된다.

**타임 칩은 가로 스크롤 한 줄.** 타임이 늘어도 세로로 접히지 않는다.

### 5. 숫자

**자리 현황은 실제 배정에서 센다.** 승인 대기(초안)와 승인만 자리를 차지하고, 거절·신청 실패·
신청 취소는 놓아준 상태다. 거절하거나 삭제하면 그 자리 숫자가 그만큼 줄어야 한다.
고정값으로 두면 승인 판단의 근거가 거짓이 된다.

자리를 쓰지 않는 유형만 보고 있을 때는 자리 현황 자체를 감춘다.

**총원은 접수 건수 기준이다.** 신청 실패·신청 취소 건도 인원에 포함한다. 자리 계획이 아니라
"몇 명이 신청했나"를 세는 숫자다. 팀은 팀원 수만큼 센다.

**목록이 비면 그 자리를 비워 두지 않는다.** 필터 결과가 없을 때 `해당하는 신청자가 없어요.`를
보여준다.

### 6. 일괄 처리

체크박스로 여러 건을 고르면 하단에 처리 바가 뜬다. 아무것도 안 고른 상태에서는 없다.

```
☐ 전체 선택                                      [거절]  [3건 승인]
```

기본이 승인이므로 **전체 선택 → 승인**이 가장 빠른 경로가 된다.

### 7. 색과 면

**흰 바탕과 회색 바탕을 번갈아 쌓아 층을 만든다.** 선을 여러 개 긋는 대신 면으로 구분한다.

| | 색 |
|---|---|
| 모달 · 헤더 | `--color-surface` 흰색 |
| 목록 영역 바닥 | `--color-bg` 연회색 |
| 신청 한 줄 | `--color-surface` 흰색, 사이 1px `--color-border` |
| **펼친 줄의 머리** | `--color-surface-sub` — 지금 보고 있는 줄임을 표시 |
| 상세 | `--color-surface` 흰색 |
| 상세 안 팀원 카드 | `--color-bg` 연회색 |
| 펼친 줄 아래 경계 | `--color-bg` 8px 띠 |

**작은 조각의 색**

| | 색 |
|---|---|
| 객관식 답 알약 | `--color-primary-light` |
| 자리 우선순위 칩 · 타임 칩 | `--color-surface-sub` |
| 파일 다운로드 | 테두리 버튼 (`btn-line-dark`) |

**상태 뱃지는 색으로 성격을 가른다.**

| 상태 | 색 |
|---|---|
| 승인 대기 | warning — 손볼 일이 남았다 |
| 승인 · 신청 완료 | success — 확정됐다 |
| 거절 | dark — 운영자가 내린 결정 |
| 신청 실패 | danger — 무효가 됐다 |
| 신청 취소 | neutral — 신청자가 뺐다 |

`거절`과 `신청 실패`를 다른 색으로 두는 것이 중요하다. 둘 다 확정이 아니지만 하나는 운영자가
만든 결과이고 하나는 아니다.

## 하지 않는 것

- **목록에 보일 항목을 고르는 설정** — 이벤트마다 다른 항목을 줄에 올리는 기능은 만들지 않는다.
  동의율 확인 같은 일은 엑셀 내보내기로 한다
- **왼쪽 목록 + 오른쪽 상세** — 상세를 자주 열지 않으므로 오른쪽 절반이 늘 빈다.
  모바일에서는 구조가 한 벌 더 필요해진다
- **전용 페이지로 분리** — 라우팅·권한·뒤로가기까지 개발이 커진다. 모달을 키우는 것으로 충분하다

## 남은 결정

**정렬 기준이 없다.** 지금은 데이터 순서 그대로라 신청일이 뒤죽박죽이다. **최신순**과
**승인 대기 먼저** 중 무엇을 기본으로 둘지 정해야 한다. 승인이 주 용도라면 후자가 맞다.

**검색이 없다.** 22명 규모면 특정 신청자를 찾을 일이 생긴다. 이름·전화번호로 거르는 입력
하나면 되지만 넣을지 정해야 한다.

**동의 여부가 줄에 없다.** 동의를 보고 판단한다고 하셨지만 신청폼 질문이라 시스템이 자동으로
줄에 올릴 수 없다. 거의 다 승인하는 흐름이라 큰 문제는 아니지만, 확인이 잦아지면 목록 컬럼을
고르는 설정을 다시 논의해야 한다.

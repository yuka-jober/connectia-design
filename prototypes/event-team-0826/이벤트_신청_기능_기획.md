# 이벤트 신청 기능 기획

청춘건배(동문 간담회) 케이스 기준 · 2026.08.26

---

## 1. 배경

### 왜 이 방향인가

모임·행사 신청 영역을 조사한 결과, 대부분의 영역은 이미 대체재가 자리 잡고 있었다.

| 영역 | 대체재 | 진입 가능성 |
|---|---|---|
| 캐주얼 무료 모임 | 오픈채팅 | 낮음 (정보 수집이 필요 없음) |
| 결제 있는 클래스 | 네이버예약 | 낮음 (결제·예약 통합됨) |
| 조직 소속 모임 | 관리자가 대행 | 낮음 (담당자에게 페인 없음) |
| 대학 공연 동아리 | 두둥 (학생팀 서비스) | 낮음 (동아리 네트워크 선점) |
| 대규모 공연 | 티켓링크·인터파크 | 낮음 |

반면 **다음 조건이 겹치는 행사**에는 적합한 도구가 없다.

- 참가자 유형이 둘 이상이고 흐름이 다름
- 팀 단위 신청이 있음
- 금전(참가비·후원금)이 오가는데 자체 결제 시스템이 없음
- 명단이 행사 후에도 자산으로 남아야 함
- 현장에서 입장 확인이 필요함

청춘건배는 이 다섯 가지에 모두 해당한다.

### 현장에서 실제로 벌어지는 일

밴드 공연 주최 경험 기준, 사전신청을 구글폼으로 받아도 현장은 수작업으로 돌아간다.

- 입장 시 사전신청 여부를 **구두로** 확인 → 줄이 밀리고 실제 대조가 안 됨
- 미신청자는 현장 입금 → 계좌 앱을 열어 확인
- 종이 명단에 이름과 목적을 손으로 적게 함 → 나중에 엑셀로 옮김
- 이 모든 게 행사 직전 10분에 몰림

이를 감당하려고 **지인에게 시간당 5,000원을 지급하고 현장 인원을 고용**했다. 공연 1회당 인건비가 실제로 발생하고 있으며, 이는 지불 의사가 이미 검증된 문제라는 뜻이다.

- **이벤트를 2개로 나눠서 운영** → 명단 분리, 통계 수동 합산, 링크 2개 배포, 참가자 오입장

- 후원금은 계좌이체 → 입금자명 불일치 시 수동 대조
- 현장 입장 확인 수단 없음

## 3. 제품 방향

### 한 문장 포지셔닝

> **신청 → 결제 → 알림톡 발송 → 현장 체크인 → 명단·정산까지 하나로 이어지는 행사 운영 도구.**

경쟁 도구는 이 흐름의 앞부분만 담당한다.

| 도구 | 신청 | 결제 | 알림톡 | 현장 체크인 | 명단 관리 |
|---|:---:|:---:|:---:|:---:|:---:|
| 구글폼 | O | X | X | X | 스프레드시트 |
| 링크트리 | X | X | X | X | X |
| 두둥 | O | 제한적 | X | O | 제한적 |
| 티켓 사이트 | O | O | 일부 | O | O (수수료·규모 제약) |
| **우리** | O | O | O | O | O |

### 핵심 차별점

**결제 시스템과 알림톡 발신 인프라를 이미 보유**하고 있다는 점이 가장 큰 진입장벽이다. 개인·학생팀은 PG 심사, 정산 구조, 알림톡 발신 프로필 승인 때문에 이 조합을 만들 수 없다.

여기에 **프로필 기반 라인업 노출**이 더해진다. 한쪽 참가자(선배·멘토·연사)의 프로필이 이벤트 페이지에 노출되고, 다른 쪽(후배·멘티·관객)이 그것을 보고 신청하는 구조는 다른 도구가 제공하지 못한다.

## 4. 기능 범위

### v1 — 이번 행사에 필요한 것

| 순위 | 기능 | 이유 |
|---|---|---|
| 1 | 참가 유형 분기 | 이벤트 1개로 통합하려면 필수 |
| 2 | 팀 단위 신청 | 재학생 신청 구조 |
| 3 | 결제 연동 (졸업생 후원금) | 입금 대조 문제 제거 |
| 4 | 참여 선배 목록 노출 | 재학생 참가 동기 · 제품 고유 가치 |
| 5 | 알림톡 발송 (신청 완료·QR·리마인드) | 안내 수작업 제거 |
| 6 | QR 체크인 + 이름 검색 | 현장 운영 |
| 7 | 통합 명단 · 상태 관리 | 주최자 운영 화면 |

### v1 제외

| 기능 | 제외 사유 |
|---|---|
| **시간 슬롯 자동 배정** | 재학생 3팀 규모에서는 수동으로 충분. 규모가 커질 때 도입 |
| 선배-팀 매칭 보드 | 위와 동일 |
| 사연 심사 화면 | 3팀 규모는 목록 확인으로 충분. 엑셀 대체 가능 |
| 참가자 로그인 강제 | 전환율 저하. 프로필은 신청 이후 선택 사항으로 |

> 시간 배정과 매칭은 **기능 자체는 유효하나 이번 규모에 맞지 않음**. 재학생 20팀 이상 규모의 행사가 생기면 1순위 후보로 재검토.

## 5. 화면 설계

### 5-1. 이벤트 작성 화면 (주최자)

기존 신청폼 섹션 위에 **참가 유형** 레이어가 추가된다. 유형이 1개면 기존 이벤트와 동일하게 동작하므로 하위 호환이 유지된다.

**유형별 설정 항목**

| 항목 | 졸업생 | 재학생 팀 |
|---|---|---|
| 신청 단위 | 개인 | 팀 (2~5명) |
| 정원 | 30명 | 3팀 |
| 참가비 | 100,000원 · 카드/계좌 | 없음 |
| 신청자 공개 | 켜짐 | 꺼짐 |

**공개할 프로필 항목** (신청자 공개가 켜진 유형만 노출)

로그인 프로필에서 자동으로 가져오며, 주최자가 항목별 공개 여부를 지정한다.

| 항목 | 출처 | 기본값 |
|---|---|---|
| 이름 | 프로필 | 공개 |
| 프로필 사진 | 프로필 | 공개 |
| 학과 · 학번 | 신청폼 | 공개 |
| 소속(직장) · 직무 | 프로필 | 공개 |
| 후배에게 한마디 | 이벤트 전용 질문 | 공개 · **필수 권장** |
| 전화번호 | 프로필 | 비공개 |

> "후배에게 한마디"를 선택 항목으로 두면 카드가 비어 보여 재학생 유입 효과가 떨어진다. 필수로 두는 것을 권장.

**신청폼 필드**

기존 이름·전화번호·이메일 고정 필드에 두 종류의 특수 필드가 추가된다.

- `팀원 목록` — 답변이 사람 레코드를 생성
- `입금자명` — 참가비 설정 시 자동 추가

일반 주관식·객관식과 달리 이 필드들은 **답변이 데이터 구조를 만든다.**

---

### 5-2. 이벤트 페이지 (참가자)

기존 구조에 `참여 선배` 섹션이 이벤트 안내 이미지 아래에 추가된다.

```
포스터 이미지
주최 조직명 / 행사명 / 일정
신청 기간 · 마감 D-day
이벤트 안내 (상세 이미지)
─────────────────────
참여 선배 (신규)
  선배 카드 × N
  [선배 N명 모두 보기]
─────────────────────
지금까지 N명이 신청했어요
[졸업생 신청] [재학생 팀 신청]
```

- 유형이 2개면 하단 버튼이 둘로 갈라진다. 1개면 기존과 동일하게 `신청하기` 하나.
- 선배 카드에 노출되는 항목은 작성 화면의 공개 설정과 1:1 대응.

---

### 5-3. 신청 흐름 (참가자)

**공통** — 신청 버튼 → 유형 선택 → 해당 폼

**졸업생**

```
유형 선택 → 로그인 (프로필 자동 생성)
  → 학과·학번·소속·후배에게 한마디 입력
  → 결제 100,000원
  → 알림톡 발송 (신청 완료 + QR)
  → 이벤트 페이지 선배 목록에 노출
```

**재학생 팀**

```
유형 선택 → 팀명·학과 입력
  → 팀원 행 추가 (이름 필수 / 연락처 선택)
  → 사연 작성 (선택)
  → 알림톡 발송 (신청 완료 + QR)
```

**팀원 입력 설계**

- 팀원 연락처는 **선택 입력**. 필수로 하면 대표자가 모른다고 이탈한다.
- 연락처가 있는 팀원에게는 개별 알림톡 발송 → 프로필 확보 기회
- 연락처가 없으면 대표자에게만 발송, 대표자가 전달
- 쉼표 구분 텍스트가 아닌 **행 단위 입력**이어야 팀원이 개별 데이터로 남는다

---

### 5-4. 관리자 명단 화면

**상단 요약** — 스크롤 없이 오늘 할 일이 보이도록

```
졸업생 18/30   재학생 3/3   결제완료 15 (미결제 3)   체크인 0/21
```

**목록 항목**

| 컬럼 | 졸업생 | 재학생 팀 |
|---|---|---|
| 이름/팀명 | 개인명 | 팀명 + 인원 |
| 소속 정보 | 학번·학과·직장 | 학과·대표자 |
| 결제 상태 | 완료 / 미결제 | 해당 없음 |
| QR 발급 | 결제 후 자동 | 신청 즉시 |
| 체크인 | 현장 스캔 시 | 현장 스캔 시 |

**액션** — 유형 필터, 미결제자 알림톡 일괄 발송, 엑셀 다운로드

---

### 5-5. 현장 체크인

**QR 스캔 결과**

```
이동욱 · 졸업생 · 2001 디자인학과
결제 완료 ✓
[입장 처리]
```

미결제자는 경고 표시 + `현장 수납 후 입장` 버튼으로 분기.

**필수 부가 기능**

- **이름·전화번호 뒷자리 검색** — QR을 못 찾는 사람이 반드시 나온다. 없으면 현장이 막힌다.
- **현장 신청 등록** — 미신청자를 즉석에서 추가
- **중복 스캔 처리** — 이미 입장한 QR은 입장 시각 표시
- **실시간 현황** — 입장 N / 신청 N

**QR 발급 방식** — 알림톡으로 발송하되, 신청 완료 화면에도 노출. 로그인 없이도 발급 가능해야 한다(전화번호만 있으면 알림톡 발송 가능).

### 5-6. 사후

- 참석 명단 / 노쇼 집계

- **이 명단으로 다음 행사 초대** — 동문회는 매년 반복되므로 명단이 그대로 자산이 된다

## 6. 데이터 구조

```
Event
 └─ ParticipantType (참가 유형)
     ├─ 설정: 신청 단위, 정원, 참가비, 신청자 공개 여부
     ├─ FormField[] (유형별 신청폼)
     └─ Registration (신청 건)
         ├─ 결제 상태, QR 코드, 체크인 상태
         └─ Participant[] (실제 사람 — 팀이면 여러 명)
```

핵심은 **Registration(신청)과 Participant(사람)의 분리**다. 팀 신청 1건에 사람 5명이 붙는 구조여야 팀 관리와 개인 식별이 동시에 가능하다.

## 8. 확장 시장

이번 조사와 외부 반응에서 확인된 인접 영역.

**1) 행사 대행사** — 대표님을 통해 관심 확인됨

- 행사를 상시·반복 운영하는 사업자
- 명단·정산·안내 발송이 곧 본업
- 학생팀 서비스가 구조적으로 진입 불가한 영역 (사업자 책임·정산·세금)
- 지불 의사 있음

**2) 인디 아티스트 · 소규모 공연장**

- 거의 전부가 링크트리를 사용 중 → **프로필 페이지 수요가 실재한다는 증거**
- 링크트리는 링크만 모으고 예매를 처리하지 못해 구글폼을 병행
- 프로필 + 이벤트 + 예매 + 체크인이 한 흐름으로 이어지면 링크 하나가 줄어드는 게 아니라 **흐름이 끊기지 않는 것**이 된다
- 팬은 반복 참여 → 프로필이 실제로 쌓이는 구조
- 티켓 사이트는 수수료·등록 절차가 부담, 두둥은 대학 동아리 중심

**3) MZ 타겟 소상공인 이벤트** — 기존 라식 케이스의 확장

- 대학생 앱 배너 → 이벤트 페이지 → 신청이라는 채널이 이미 검증됨
- 다만 현재는 세팅과 데이터 전달을 우리가 대행하는 구조 → 제품화 필요

## 9. 이번 행사에서 검증할 것

기능 판단 근거를 숫자로 남긴다.

| 측정 항목 | 왜 필요한가 |

## 10. 오픈 이슈

| 이슈 | 내용 |
|---|---|
| 결제 수수료율 | 두둥이 무료라 가격 비교가 발생할 수 있음. 결제·알림톡 포함 시 다른 카테고리임을 설명할 근거 필요 |
| 알림톡 발신 명의 | 주최자 명의 발송 가능 여부. 대행사는 자사 브랜드로 보내길 원할 가능성 |
| 소액 결제 부담 | 1~2만원대 참가비에서 수수료 비중 |
| 프로필 확보와 전환율 | 참가자 로그인 강제는 전환율을 떨어뜨림. 프로필은 신청 이후 선택으로 두는 방향 제안 — 우선순위 확인 필요 |
| 졸업생 프로필 작성 마찰 | 후원금까지 내는 상황에서 프로필 입력이 부담이 될 수 있음. 최소 항목으로 시작 |

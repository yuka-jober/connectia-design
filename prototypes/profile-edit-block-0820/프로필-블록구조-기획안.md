# 프로필 페이지 블록 구조 전환 기획안

작성일: 2026-08-20 · 상태: 리뷰 요청

---

## 1. 배경과 목적

커넥티아를 link in bio 카테고리로 광고하기로 결정함에 따라, 프로필 페이지도 해당 카테고리의 실제 사용 방식에 맞춰야 한다.

해외 소규모 사업장의 링크트리 약 40개를 확인한 결과 두 가지가 확인됐다.

1. **대부분 오직 링크를 나열하는 용도로만 사용한다.** 사진·긴 설명을 채운 경우는 드물었다.
2. **내용은 간소해도 디자인은 거의 모두 꾸며두었다.** 색상·버튼·배경을 브랜드에 맞춰 조정했다.

현재 커넥티아는 정해진 섹션을 채우는 구조라, 링크를 개별적으로 배치·강조할 수 없고 디자인 변경 폭도 좁다. **카테고리의 가장 기본적인 사용 방식을 지원하지 못하는 상태**다.

**목적** — 프로필 페이지를 링크 중심의 자유 배치 구조로 전환하고, 디자인 커스터마이징 범위를 넓힌다.

---

## 2. 현재 구조와 문제

현재 편집 화면은 **폼(form)** 이다. 다음 세 가지 가정 위에서 성립한다.

| 가정 | 블록형에서 깨지는 이유 |
|---|---|
| 섹션이 타입당 1개 | 링크가 20개면 "링크"라는 제목이 20번 반복됨 |
| 개수가 고정(7개) | 모든 에디터를 펼쳐두면 스크롤이 감당 불가 |
| 순서가 고정 | "여기에 끼워 넣기"라는 개념이 UI에 없음 |

또한 현재 링크는 하나의 섹션 안에 묶여 있어 **"링크는 항상 연속으로만 배치된다"** 는 제약이 있다. 링크 사이에 텍스트나 이미지를 넣을 수 없다.

## 3. 변경 방향 요약

| 항목 | 현재 | 변경 후 |
|---|---|---|
| 링크 | 1개 섹션에 묶임 | **링크 1개 = 블록 1개** |
| 텍스트·이미지 | 섹션당 1개 | **여러 개 추가 가능** |
| 게시판·리뷰·이벤트 | 섹션당 1개 | **유지 (1개)** |
| SNS | 1개 섹션 | **유지 (묶음)** |
| 순서 | 섹션 단위 | **블록 단위 자유 배치** |
| 디자인 | 템플릿 선택 | **전역 테마 + 개별 예외** |
| 편집 화면 | 고정 폼 | **결과가 보이는 캔버스** |

## 4. 블록 분류

블록을 성격에 따라 세 종류로 나눈다. 규칙이 다르기 때문에 UI와 데이터 처리를 구분해야 한다.

| | 콘텐츠 블록 | 묶음 블록 | 컬렉션 블록 |
|---|---|---|---|
| 종류 | 링크, 텍스트, 이미지, 구분선 | SNS | 이벤트, 게시판, 리뷰 |
| 개수 | 제한 없음 | 1개 | 1개 |
| 편집 | 반쪽 시트 | 반쪽 시트 | 반쪽 시트 + 전체 화면 관리 |
| 삭제 | 삭제 시 소멸 | 숨김만 | **숨김만 (삭제 없음)** |
| 데이터 | 블록이 곧 데이터 | config 배열 | 별도 테이블 참조 |

### 왜 SNS는 쪼개지 않는가

인스타·유튜브 아이콘은 한 줄로 나란히 배치돼야 의미가 있다. 개별 블록으로 분리하면 아이콘이 세로로 흩어져 형태가 무너진다. 아이콘 배열 자체가 UI인 묶음형으로 유지한다.

### 왜 컬렉션 블록은 1개만 두는가

게시판·리뷰·이벤트는 별도 데이터를 소유한다. 여러 개를 허용하면 "어느 게시판에 글이 속하는가"를 정의해야 하고, 삭제 시 기존 데이터 처리 문제가 생긴다. MVP에서는 싱글톤으로 두되, **블록 테이블에 `ref_id`를 미리 두어 추후 다중 허용 시 마이그레이션 없이 확장 가능하게 한다.**

## 5. 데이터 구조

```
profile (handle, 이름, 커버, 아바타)          ← 공용
  └ page (type, theme)
      └ block (kind, sort, visible, config, ref_id)
```

- 기존 섹션 설정은 이미 `kind / sort / visible`을 보유하고 있어 그대로 block 레코드로 전환 가능
- **기존 프로필 = 시스템 블록이 미리 꽂혀 있는 블록 페이지**로 재정의
- 클래식/블록형은 별개 제품이 아니라 **프리셋(초기 블록 구성 + 테마)의 차이**

### 중첩 정책

블록 간 부모–자식 구조(그룹/폴더)는 **이번 범위에서 도입하지 않는다.** 중첩 드래그앤드롭은 모바일에서 실패율이 높고 렌더링 예외가 급증한다. 링크가 많아졌을 때의 구획은 **구분선·제목 블록으로 시각적으로만** 처리하고, 구조는 평면(flat)으로 유지한다.

---

## 6. 마이그레이션

**원칙: 기존 사용자에게 보이는 화면은 달라지지 않는다.**

1. 기존 링크 섹션 → N개의 link 블록으로 평면화
2. 원래 순서를 `sort`에 승계 (섹션 sort를 기준점으로, 내부 순서를 간격 배분)
3. 나머지 섹션 → 각 시스템/컬렉션 블록으로 1:1 전환
4. 게시글·리뷰·이벤트 데이터는 그대로 참조 유지

전환 후에도 링크들은 연속으로 붙어 보이고 순서도 동일하다. **달라지는 것은 이제 그 사이에 다른 블록을 넣을 수 있다는 점뿐이다.**

## 7. 편집 화면 설계

### 설계 목표

- 편집 화면에서도 **실제 프로필의 모습을 그대로 예측**할 수 있을 것
- 링크 블록이 **수십 개로 늘어나도** 편집과 정렬이 번거롭지 않을 것

### 핵심 전환: 폼 → 캔버스

과거 편집을 시트로 분리했을 때 "결과가 안 보인다"는 피드백을 받은 바 있다. 다만 그 원인은 "접었기 때문"이 아니라 **접힌 상태에서도 시트 안에서도 결과를 보여주지 않았기 때문**이다. 현재의 펼친 폼 역시 입력 필드일 뿐 결과가 아니다(마크다운 지원이라면서 렌더링 결과는 보이지 않음).

따라서 다음과 같이 해결한다.

**블록 카드를 입력 폼이 아니라 실제 렌더링 결과로 그린다.** 링크 블록은 실제 버튼 모양으로, 텍스트 블록은 렌더링된 텍스트로 표시한다. 접혀 있어도 이미 결과가 보인다.

**편집은 화면 절반만 덮는 시트로 연다.** 편집 중인 블록이 시트 위에 계속 보이고, 타이핑하는 대로 실시간 반영된다.

**입력 도구는 편집 중에만 노출한다.** 툴바·글자수·AI 학습 토글·안내 문구는 시트 안으로 이동. 평소 캔버스에는 결과만 보인다.

### 주요 인터랙션

| 요소 | 동작 |
|---|---|
| 블록 카드 탭 | 반쪽 시트 편집 열기 |
| 블록 사이 `+` | 그 위치에 블록 추가 (카탈로그 시트) |
| 좌측 레일 ▲/▼ | 한 칸씩 순서 이동 (첫/마지막은 비활성) |
| 좌측 레일 드래그 핸들 | 멀리 이동 |
| 미리보기 토글 | 레일·삽입점·배지 숨김 → 실제 프로필과 동일 |

**주의사항**
- 화살표는 아이콘만 노출하되 **탭 영역은 44pt 확보**
- 편집 중 블록 이동 시 시트는 유지하고 스크롤이 따라감
- 키보드 노출 시 시트 위 공간이 좁아지므로, 편집 진입 시 해당 블록이 잔여 영역에 오도록 스크롤 자동 조정

## 8. 디자인 설정 구조

### 2단 구조: 전역 테마 → 블록 오버라이드

디자인 설정은 블록이 아니라 **페이지 속성**이므로 블록 목록에 섞지 않고 상단 별도 진입점(팔레트)에 둔다.

**전역 (팔레트 → 3개 탭)**

| 탭 | 항목 |
|---|---|
| 커버 | 프로필 사진 배치, 정렬, 배경 |
| 버튼 | 모서리(각짐/둥금/알약), 채우기(흰 카드/채움/테두리) |
| 색상 | 테마 색상 (커버·버튼·SNS 아이콘 공통 적용) |

**블록 개별 (편집 시트)**
- "이 블록만 강조" → 전역 설정을 덮어씀. 특정 링크만 부각할 때 사용
- 오버라이드는 소수 항목만 허용해 관리 복잡도를 억제

### 커버 = 프로필 사진 배치

커버 설정은 배경 이미지 선택이 아니라 **프로필 사진을 어디에 둘지**를 정하는 항목이다.

| 옵션 | 설명 |
|---|---|
| 배경 위에 겹치기 | 프로필 사진이 커버 하단에 걸침 (현재 방식) |
| 배경 아래 따로 | 겹치지 않고 커버 아래에 배치 |
| 그라데이션 | 배경이 아래로 흐려지며 프로필 사진이 그 위에 얹힘 |
| 사진 없이 | 아바타 없이 이름부터 시작 |

여기에 정렬(왼쪽/가운데)과 배경(이미지/단색)을 조합한다.

### 표시 방식은 전역이 아닌 블록 속성

버튼형/카드형(썸네일)은 스타일이 아니라 **콘텐츠 구조(썸네일 유무)** 이므로 블록 쪽에 둔다. 전역에 두면 모든 링크가 썸네일을 요구하게 된다.

**예외 처리**: 썸네일 카드는 전역 모서리 값을 따라가되 **최대 16px에서 멈춘다.** 알약(999px)을 선택해도 카드는 둥근 사각을 유지한다. 버튼과 카드는 형태가 달라 같은 값을 공유할 수 없다.

## 9. 컬렉션 블록 상세 정책

### 삭제 없음, 숨김만

게시글 수십 개가 달린 블록에 삭제 버튼을 두면 사고가 발생한다. 토글로 페이지에서만 내리고 데이터는 유지한다. 시트에 다음을 명시: *"삭제 대신 표시만 꺼집니다. 등록한 N개는 그대로 남아요."*

### 캔버스에는 요약본만

게시글 50개를 캔버스에 모두 그릴 수 없다. **공개 페이지도 "최근 N개 + 더보기"로 렌더링**하도록 설계해 "결과를 그대로 보여준다"는 원칙을 유지한다.

### 편집 시트에는 표시 옵션만

내용 등록은 반쪽 시트로 불가능하므로 전체 화면으로 전환한다. 시트에는 다음만 둔다.

- 블록 제목 (예: "Board" → "공지사항")
- 레이아웃 (리스트 / 카드 / 가로 슬라이드)
- 노출 개수 (3 / 5 / 전체)
- 정렬 (최신순 / 직접 지정)

### 진입 버튼은 정렬 설정에 따라 분기

- **직접 지정** → 순서 변경 화면 (항목별 ▲▼로 노출 순서 조정)
- **최신순** → 관리 화면 (등록·수정)

순서 변경 화면에서는 **노출 개수를 넘는 항목을 흐리게 처리하고 "프로필에 표시 안 됨"을 명시**한다. 순서와 노출 개수가 맞물리는 지점이라, 표시하지 않으면 "왜 안 보이지?" 문의가 발생한다.

### 빈 상태는 편집 화면에서만

"아직 등록된 이벤트가 없어요"는 편집 화면 전용이다. **방문자에게는 빈 블록을 노출하지 않는다.**

### 리뷰만 다른 점

리뷰는 데이터를 방문자가 생성하므로 설정이 다르다.

- 리뷰 받기 on/off — **블록 숨김과 별개**. 숨겨도 수집은 계속됨
- 승인 후 공개 / 자동 공개
- 신고·차단 처리

"블록을 숨긴다"와 "리뷰 받기를 중단한다"를 UI에서 명확히 구분해야 한다. 하나의 토글로 묶으면 반드시 문의가 발생한다.

## 10. 클래식 ↔ 블록형 전환

**완전 분리하지 않는다.** 프로필 주소·아바타·커버는 공유하고 페이지 타입만 분기한다.

**전환은 비파괴로 설계한다** — 전환 시 데이터를 삭제하지 않고 노출 여부와 정렬만 변경한다. 블록형으로 갔다가 돌아와도 게시글·리뷰가 그대로 있어야 한다. 이 보장이 있으면 "돌아올 수 없는 선택"이 아니게 되어 온보딩 부담이 사라진다.

단, 페이지 타입별로 유효 범위가 다른 스타일 설정(예: 대화하기 버튼의 하단/코너/내부)은 전환 시 유지되지 않을 수 있으므로 고지가 필요하다.

## 11. 이번 범위에 포함하지 않는 것

- 신규 템플릿 제작, 폰트 변경
- 블록 그룹/폴더 (중첩 구조)
- 컬렉션 블록 다중 허용
- 블록별 예약 노출(기간 설정)
